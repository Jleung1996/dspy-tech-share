What DSPy is

A Python toolkit for LLM systems: you describe the job, and a scoring test decides whether a change to the instructions helped.

The trade

DSPy doesn't remove prompt engineering. It moves it.

You write the prompt by hand
→
A model writes it against your metric
You cannot tell whether a change helped
→
The same cases give you one number
Your rules are prose the model may ignore
→
Your rules are code the model cannot break
Cheap to start, expensive to change
→
Expensive to start, cheap to change

What it buys

Improvement you can defend, and rules that cannot be ignored.

What it costs

A metric and a labelled set. Our run: 120 calls, 12 of 14 proposals still worse than the human prompt.

Use it, or don't

Use DSPy when

  • You will run it many times, so the setup cost pays itself back.
  • Correctness can be checked by code, or by a judge you have validated against humans.
  • You expect to change the model, the provider or the rules — anything you would otherwise re-prompt by hand.

Do not use it when

  • You will call it five times. Write the prompt — you will save yourself an afternoon.
  • Nobody can define "correct". There is nothing to optimise against, and that is the problem to fix first.
  • A deterministic function already gives the right answer. Never put a model near arithmetic or a risk mapping.

5. The metric

One idea: a benchmark earns credit for how close its relationship is, and loses more for being wrong than it gains for being adequate.

credit = ( peers × 1.0  +  adjacent × 0.5 ) / 3
penalty = 1.5 × ( wrong / 3 )
score = clamp01( credit − penalty )
clamp01 // keep it between 0 and 1 — floor at 0, cap at 1
duplicate // the three picks are really one option → score × 0.8
unusable // wrong count, unknown id or a repeated id → score = 0

A peer is worth two adjacents. A wrong pick costs three times what an adjacent earns. A duplicate means either three funds tracking one industry, or any pair whose descriptions are 60% similar — two trackers of the same index are one option, not two.

The optimiser only ever ranks on validation. If the test set were used for ranking, the reported score would be the score of the winner chosen by that same test set — and the improvement would be partly an artefact.

2. MIPROv2 — generate, rank cheaply, promote the survivors

MIPROv2 writes every candidate before it scores anything. Then it runs a cheap, noisy tournament and only pays for full evaluation on the few that survive it. The proposer never sees a failure, so there is nothing for it to learn from mid-search.

One score per checkpoint, written here as it happens. The final comparison reads nothing else — which is why the winner can be from round 2 rather than round 3.

The six are trials, not six different prompts: the same prompt can be re-tested several times, and that is exactly how its average sharpens. And the one promoted is the best average that has not yet had a full exam, so nothing is fully tested twice.

What gets generated, and what is actually random

Instruction candidates — written, not sampled

An LLM proposer writes them, guided by a summary of your dataset plus a random “tip” each time so they differ. You do not pick from a pool of existing prompts; they are generated once, up front, and never revised mid-search.

Count: num_candidates if optimizing zero-shot only, but half that when demos are also being optimized — the budget is deliberately shifted to demos. So auto="light" gives 3 instructions × 6 demo sets = 18 combinations, not 36.

Demo sets — built, with randomness inside

Three are fixed by construction, the rest are bootstrapped:

D0zero-shot — no examples at all
D1labelled only — real input/output pairs
D2bootstrapped — the program's own traces, kept only where the metric passed
D3+shuffle the trainset, pick a random demo count, bootstrap again

You never supply these. MIPROv2 builds all N of them itself, from the trainset you pass in, before it proposes any instruction — and then shows them to the instruction proposer, so the two are written to fit each other.

So: instructions are generated, demo sets are constructed with a shuffle and a random size, the (instruction, demo) pairing is searched by Optuna rather than picked at random, and the only purely random draw in each trial is which validation cases land in the minibatch.

GEPA does not do this at all. It builds no demo sets — it only rewrites instructions, which is why its metric has to return a sentence to learn from.

Why the toy assumes a big validation set

The cheap stage only switches on when the validation set is larger than 50 cases. Below that, every trial is already a full evaluation — no minibatches, and no budget saved by having them.

Our validation set is 3 cases, so the ten-question exam in the toy is the general case, not ours. If we had run MIPROv2 on this task, its funnel would have collapsed to plain full evaluations.

MIPROv2 was never our optimiser — it is the comparison. We ran GEPA, which needs no minibatch machinery.

Two things this tidy example hides. First, the parent for each loop is selected from the frontier, not automatically the previous child. Usually it is the previous child — but the selector is free to reach back to an earlier candidate that is still best on some cases, so the lineage can branch. Second, the scores rise here only because the example is tidy: in a real run most children come back worse. Ours kept 2 of 14, and the twelve that lost were discarded.

So it does compound — each child inherits its parent's wording and adds one correction — but it compounds on a frontier, not on a single line, and the returned prompt is the best on validation, which may be an earlier branch rather than the latest one.

Every accepted addition is traceable. “prefer same-industry peers” came from peer=1; “do not pick two funds” came from same exposure. Reflection never rewrites the whole prompt — it appends the one rule that addresses the sentence in front of it.

And that is exactly why loops 3–5 failed. Once the metric says “nothing specific left to fix”, reflection has no complaint to answer, so it invents one — a word limit, a market-cap preference — and every guess scores lower. The rejections are not a bug: 2 of our 14 real proposals survived. A loop that produces nothing better is the normal case, and a child that wins nowhere simply never reaches the frontier.

Two differences that matter. MIPROv2 writes all its candidates first and then selects; GEPA writes one, reads the failure, and rewrites — so it needs a metric that explains itself. And MIPROv2 ranks by average, while GEPA ranks per case, which is how our run produced a prompt that fixed three held-out cases and left seven untouched: a specialist, not a generalist.
