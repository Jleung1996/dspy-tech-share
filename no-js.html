What DSPy is, and what it can do

A Python toolkit for LLM systems: you describe the job, and a scoring test decides whether a change to the instructions helped.

The problem it solves

You write a prompt. It works in the demo. Then you change the model, add a rule, or tune it for one more client, and you cannot tell whether it got better or worse. Every change is a guess judged by eyeballing a few outputs. DSPy's answer is to stop treating the prompt as the thing you edit and start treating it as an output you measure.

hand-promptedwith a score
prompt v1?0.61
prompt v2?0.77
prompt v3?0.58

Same three prompts. The only difference is a test that returns a number.

How the framework is shaped

Five pieces, in order. The plain name is what it means; the grey name is what you would type.

stepplain namewhat it isDSPy name
1The taskwhat goes in, what comes outSignature
2The methodone answer, or reason first, or use toolsModule
3The pipelinesteps joined together in PythonModule subclass
4The scorea test that says right or wrongMetric
5The editorrewrites the instructions to raise the scoreOptimiser

Closest familiar thing: a compiler. You write what you want in a readable form; a compiler produces the low-level instructions. DSPy does that for prompts. Unlike a compiler, the "correct output" has to come from your own test score, which is why the score is the hard part.

A single call, end to end

movewhat happens
1. DeclareThe fields you want, with types, plus one sentence saying what the job is.
2. Build promptA formatter turns that declaration into instructions for the model.
3. Model answersOne API call to whichever model you configured.
4. ParseThe text is converted back into real data: lists, numbers, fixed options.
5. Typed objectYou ask for result.answer. A wrong shape raises instead of passing silently.

No prompt is stored in your code. It is built fresh each call from your declaration plus whatever the editor last wrote, which is why changing model does not throw away your work.

Signatures — Specify what you want, not how dspy.Signature · InputField · OutputField

What it is

A signature is a typed description of one task. It says which inputs go in, which outputs must come out, and what type each one is. It is a Pydantic model underneath, so the reply is validated against the declared types instead of being passed along as loose text. The class docstring is the instruction - the one string an optimiser may rewrite.

What goes into it

ingredientwhat it does
the docstringthe instruction. This is the only part an optimiser may rewrite.
InputFielda value the caller supplies. Never generated.
OutputFielda value the model must produce. Validated on parse.
typesstr, int, Literal[...], nested models, list[...]. A literal turns "pick a category" into a closed set.
field orderpreserved, and it is the order the model sees. Inputs come first.

A simple example

class Sentiment(dspy.Signature):
    """Is this product review positive or negative?"""
    review: str = dspy.InputField()
    label: Literal["positive", "negative"] = dspy.OutputField()

classify = dspy.Predict(Sentiment)
classify(review="Battery dies in an hour.")

Nothing here is a prompt. The docstring is the task, the two fields are the contract, and Literal means the model cannot answer 'mixed' - the parser would reject it.

In our case

Our benchmark task, in full:

class SelectEquityBenchmarks(dspy.Signature):
    """Pick three defensible benchmarks for one holding."""
    holding: str = dspy.InputField(desc="equity, with exposure facts")
    risk_level: str = dspy.InputField(desc="pre-mapped upstream")
    shortlist: str = dspy.InputField(desc="permitted benchmark ids")
    look_through_analysis: str = dspy.OutputField()
    selections: list[PickModel] = dspy.OutputField()

And what that produces for NVIDIA:

Prediction(
  look_through_analysis='US semiconductor exposure; valuation and exposure
                         currency both USD, so no wrapper adjustment.',
  selections=[PickModel(benchmark_id='EQ_AMD', role='dominant_sleeve', ...),
              PickModel(benchmark_id='EQ_TSM', role='dominant_sleeve', ...),
              PickModel(benchmark_id='IDX_SOX', role='diversifier', ...)]
)

Two things are absent on purpose. There is no name field, so the catalogue name is a dictionary lookup and cannot be paraphrased. And there is no numeric field, so the model has nowhere to put an invented return.

Limitation

Limitation. Types guarantee the shape, never the truth: a field typed str can hold a confident wrong answer. And every field you declare is one more thing the model must produce on every single call.

There is no "avoid" case, and that is worth saying out loud

A signature is not a technique you opt into - it is what a DSPy call is. Even dspy.Predict("question -> answer") builds one behind the scenes from that string. So the decision is not whether, but three others: which fields, how tight the types, and when to stop adding.

Modules — Structure your program logically dspy.Predict · ChainOfThought · ReAct · RLM · BestOfN · Refine

What it is

A module is the strategy wrapped around a signature. The signature says what the task is; the module decides how to get there - one direct call, think first then answer, or a loop that calls tools. Swapping the module never changes the task definition, which is what makes strategy cheap to trial.

What goes into it

modulewhat it addscalls
Predictnothing - one straight call1
ChainOfThoughta reasoning field before the answer1
ReActa loop: choose a tool, read the result, repeat1 per turn
BestOfNN samples, keep the best by your reward functionN
RefineN samples, feed the failure back in as a hintN

A simple example

# the same signature, three strategies
dspy.Predict(Sentiment)(review=text)          # answer straight away
dspy.ChainOfThought(Sentiment)(review=text)   # reason, then answer
dspy.BestOfN(dspy.Predict(Sentiment), N=5,
             reward_fn=is_confident, threshold=1.0)(review=text)

One task, three different amounts of effort and cost. The signature was written once and never touched.

In our case

We used ChainOfThought, because picking benchmarks is judgement rather than extraction - a direct call kept returning the first plausible index.

program = dspy.ChainOfThought(build_signature())
pred = program(holding=..., risk_level=..., shortlist=...)

The cost of that choice, measured: one extra reasoning field per call, and the reasoning is not auditable - it reads sensibly whether or not the picks are right. In 3.5 it is also no longer a plain string; it is dspy.Reasoning | None.

Limitation

Limitation. Each step up costs tokens and latency; BestOfN at N=5 is five times the bill. And a module changes how the model reasons, never what it knows - no strategy recovers a fact that was missing from the input.
Tools — Interact with the outside world dspy.Tool · dspy.ReAct · MCP · PythonInterpreter

What it is

You write the tool; the model only decides when to call it. A tool is an ordinary Python function - your code, your side effects, your permissions. The model picks which function to call, with which arguments, reads the result, and decides whether to call another. Your function's docstring is what the model sees, so in DSPy a docstring is prompt text.

What goes into it

ingredientwhat it does
the functionanything callable. Typed arguments become the argument schema.
the docstringthe description the model reads. Vague docstring, vague tool.
a ReAct modulethe loop that decides when to stop calling.
a turn budgetwhat stops it looping forever. Always set one.

A simple example

def get_weather(city: str) -> str:
    """Current weather for a city."""
    return api.weather(city)

agent = dspy.ReAct("question -> answer", tools=[get_weather])
agent(question="Do I need a coat in Tokyo?")

The model never writes this function. It reads the docstring, decides the function is relevant, supplies the argument, and reads what comes back.

In our case

We did not use tools in the run you are looking at, and that was a cost rather than a design win.

The task read only what was supplied in the prompt: an id, a name, a sector, a country. The enrichment most likely to move the score - industry codes and measured co-movement per candidate - is exactly what a tool supplies.

def co_movement(asset_id: str, candidate_id: str) -> float:
    """Trailing 2y correlation of daily returns, market-adjusted."""
    return prices.residual_corr(asset_id, candidate_id)

With that tool the model could check a candidate instead of guessing from its name. Without it, the only lever left was the wording of the instruction - which is precisely where the optimiser plateaued.

Limitation

Limitation. Tools are capability you pre-wrote, so they cannot cover a case you did not foresee. Every call can fail, and failures compound inside a loop. And every tool is an attack surface, because the model chooses the arguments.

Programmable, or generated?

you need...who writes ituse
a capability you can write today; only the when is uncertain youa plain function + dspy.ReAct
the model to compute something by writing and running code the modeldspy.RLM
a fixed sequence you know in advance youjust call it - no model, no tool

The test is one question: can you write the function today? If yes, it is a tool. If the function itself is the hard part, you want code generation.

Adapters — Customizable prompt formatters XMLAdapter · ChatAdapter · JSONAdapter

What it is

The adapter is the layer between a signature and tokens. It renders the instructions, the field schema and any demos into an actual prompt, then parses the reply back into your declared types. The same signature through two adapters is two different prompts and two different parsers - so the adapter is part of the system, not a formatting detail.

What goes into it

ingredientwhat it does
instructionsthe signature docstring, placed as the system message.
field schemanames, types and descriptions, rendered into the prompt.
demosfew-shot examples an optimiser selected, if any.
the parserturns the reply back into typed objects. This is what rejects bad shapes, and what triggers a retry.

A simple example

dspy.Predict(Sentiment)     # built once
# with XMLAdapter the model is asked for:   <label>negative</label>
# with ChatAdapter it is asked for:         [[ ## label ## ]] negative
# with JSONAdapter it is asked for:         {"label": "negative"}

Identical signature. The only difference is what the model is told to emit, and how strictly the reply is parsed.

In our case

This one was not academic - the adapter decided whether the project ran at all.

same signature, same model (deepseek/deepseek-flash):
  JSONAdapter   -> LMInvalidRequestError: response_format unavailable
  XMLAdapter    -> 30 cases run, 7 failed to parse
  ChatAdapter   -> 5/5 parse on exactly those failing cases

Switching XML to Chat took parse failures from 23% to 3% without changing one character of the task definition. The first version of the run was measuring the adapter, not the prompt.

Limitation

Limitation. 3.5 changed the default from Chat to XML, so upgrading silently changes every prompt you already have; anything optimised before the upgrade must be re-measured. And providers that reject response_format need the JSON fallback explicitly disabled.
Optimizers — Optimize your program, ML-style dspy.GEPA · MIPROv2 · BootstrapFewShot · COPRO · SIMBA

What it is

An optimiser proposes changes, scores each one with your metric, and keeps only what wins. Every optimiser tunes one or more of exactly three knobs - the instructions, the demos, or the model weights. Nothing else is in the search space; the schema, the gates and your evaluation set stay frozen, which is what stops it cheating.

What goes into it

ingredientwhat it does
your metricthe only definition of better. Also the budget unit.
a trainsetcases it may optimise against.
a valsetcases it uses to choose between candidates. Keep it separate.
a proposerwrites new instructions. For GEPA this is a second model.
a budgetmax_metric_calls. This, not a prompt count, is what bounds the run.

A simple example

# the cheapest optimiser: keep a few good examples as demos
opt = dspy.BootstrapFewShot(metric=metric, max_bootstrapped_demos=3)
better = opt.compile(student=program, trainset=trainset)

No reflection model, so it costs a fraction of GEPA. It only selects demos - it never rewrites your instruction.

In our case

We ran GEPA, which rewrites the instruction and reads your metric's feedback while doing it.

21 iterations, 14 proposals written, 120 metric calls
v0  0.635   the prompt a human wrote
v1  0.738   kept
v2  0.767   kept  <- best
v3..v14     all worse than v2, discarded

12 of 14 proposals did not beat the human prompt

The improvement is real but narrow: GEPA fixed three of ten held-out cases to a perfect score and left the other seven untouched. It could not help where the input was the limitation rather than the wording.

Limitation

Limitation. Hundreds of model calls, and most candidates come back worse than where you started. An optimiser cannot add a fact the model lacks, cannot reorder the shortlist it was given, and cannot fix a metric that rewards the wrong thing.

They are not interchangeable

optimisertunesreach for it when
GEPAinstructions your metric returns feedback text, not just a number
MIPROv2instructions + demos both look weak and you have budget
BootstrapFewShotdemos first thing to try; costs almost nothing
BootstrapRSdemos, random search demo quality varies between draws
COPROinstructions only fast shallow sweep without a feedback metric

BootstrapFinetuneweights prompt-only has plateaued and the model is tunable

All of them return a new program and leave the original untouched, so the same student can be compiled three ways and compared.

Metrics — Define what to optimize against any callable · dspy.Evaluate · SemanticF1

What it is

A metric is a function taking (gold, prediction) and returning a number - or, far better, a number and a sentence of feedback. The number decides keep or discard. The sentence is what the optimiser's reflection step reads, and it is the whole reason a rewrite can be targeted rather than random. The optimiser's budget is counted in calls to this function.

What goes into it

ingredientwhat it does
goldthe labelled example: what the right answer is.
predwhat the program produced this time.
traceoptional. Lets a metric behave one way at evaluation time and another inside an optimiser.
the return valuebool, float, or Prediction(score, feedback).
feedbackthe sentence GEPA reads. Omit it and reflection has nothing to work from.

A simple example

def exact(gold, pred, trace=None):
    return gold.answer.strip().lower() == pred.answer.strip().lower()

The simplest legal metric: True or False per example, averaged into a percentage. It works - but it gives the optimiser no reason, so reflection can only guess what to change.

In our case

Ours is four layers, applied in this order:

1. hard gates      wrong count / unknown id / duplicate   -> score 0
2. tiered credit    peer 1.0 + adjacent 0.5, divided by 3
3. soft penalties   -0.12 per broken rule (word limit, banned word, ...)
4. feedback text    "peer=1 adjacent=2 wrong=0. Prefer same-industry peers."

And the sentence that actually drove the optimisation:

EQ_NVDA: scored 0.55 with ['IDX_SOX', 'ETF_XLK', 'IDX_SPX'].
peer=1 adjacent=2 wrong=0. Prefer same-industry peers over broad indices;
acceptable examples were ['EQ_AMD', 'EQ_ASML', 'EQ_AVGO'].

Everything after peer=1 is guidance a scalar score could never carry. Drop it and the optimiser is not merely weakened - GEPA substitutes "This trajectory got a score of 0.55", and the loop stops learning.

Limitation

Limitation. The metric becomes the objective, so any hole in it gets exploited, and an automated search finds holes faster than a human does. Ours is also a proxy: it scores 0 on a genuine peer it cannot see, and carries roughly ±0.08 of noise on ten cases.

What makes a metric trustworthy

propertyfails like this
Discriminativeevery candidate scores 0.9 - no gradient, nothing to climb
Ungameablea junk answer scores well, and the optimiser finds it
Alignedit improves while the real outcome gets worse
Cheapyou cannot afford 120 calls, so you optimise blind
Stablethe same input scores differently on reruns; you chase noise

The trade

good fitbad fit
The job splits into steps, correctness is checkable by code, and you expect to change models.You will run it five times, or nobody can define correct, or a plain function already answers it.

What our own measurement cannot tell you

limitwhy it matters

The setup, and what DSPy does with it

One real task: given an equity, pick three defensible benchmark references. NVDA should get AMD or TSMC, not Salesforce.

1. What we hand to DSPy

DSPy adds three things we did not write: the signature (shape of the answer), the program (the call), and the optimiser (the rewriting loop).

2. Where the metric came from

Nobody hands you a metric. It is built, mostly from failure analysis. Four steps: start from the cost, curate truth in tiers, pick weights openly, automate the checks.

Hard negatives are the ones that matter. Anyone can reject oil for a chip company. Only a real analysis rejects a software company for a chip company, which is why five Salesforce-class ids sit in their own tier. Nothing here was inferred by a model.

The same three picks (AMD + TSM + CRM) under three different penalties, which is why the weights are published rather than buried:

At 0.5 a peer-less answer still scores respectably. At 3.0 it collapses. Same answer, different metric, different conclusion.

3. What a score actually is

The score is not a similarity rating. It is a small additive rule over the three ids returned: peer 1.0, adjacent 0.5, wrong -1.5, divided by three, then penalised for duplicate exposure.

How the optimiser works

Neither optimiser is doing anything mystical: write a candidate prompt, score it, keep it if it is better. They differ in when the prompt is written, and in what counts as better.

1. The loop

Training set — the cases the optimiser rewrites the instruction against.
Validation set — ranks the survivors; this decides which prompt is best.
Test set — never enters the search. It only produces the number we report.

The optimiser only ever ranks on validation. If the test set were used for ranking, the reported score would belong to the winner that same test set chose.

2. MIPROv2 — generate, rank cheaply, promote the survivors

  1. Generate every candidate up front, before any scoring.
  2. Score cheaply — one random minibatch of the validation set per trial.
  3. Rank by the average of the noisy draws, not one lucky batch.
  4. Promote the leader to a full evaluation on the whole validation set, every six trials, and feed that result back to the search.
  5. Return the program with the best full-evaluation score.

Instruction candidates are written by an LLM proposer guided by a dataset summary and a random tip, once, up front. Demo sets are constructed: zero-shot, labelled-only, bootstrapped, then shuffled bootstrapped sets with random sizes. The pairing is searched by Optuna, not picked at random. The only purely random draw per trial is which validation cases land in the minibatch. At auto="light" with demos enabled that is 3 instructions × 6 demo sets = 18 combinations.

Minibatch mode only engages above 50 validation cases. With our 3-case valset, every MIPROv2 trial would already be a full evaluation.

3. GEPA — write, read, rewrite

  1. Sample a minibatch (default 3 cases) and run the current candidate with trace capture.
  2. Score it. The metric returns a number and a sentence. That sentence is the input to the next step, and it is why the metric has to say why.
  3. Reflect. A second model reads the failures and rewrites the instruction — a targeted edit, not a paraphrase.
  4. Accept on the Pareto frontier. A child is kept if it beats its parent on any case, not just on average.

A plain average rewards a prompt that is mediocre everywhere. Per-case tracking keeps one that is excellent on semiconductors and bad on utilities, because it may still contribute later. In our run that produced a prompt which fixed three held-out cases and left seven untouched.

4. Side by side

MIPROv2: writes its candidates up front, Optuna scores the pairs, keeps the highest average, selects from a fixed grid.
GEPA: writes one instruction, reads the critique, writes the next one, and keeps a child if it wins anywhere — a reflection search rather than a grid.

Both return a new program and leave yours untouched. Both are bounded by the same thing: the metric. Neither can add a fact the model does not have.
